# microdocs — требования

Документ ведётся по шагам: продуктовые → функциональные → нефункциональные.
Статус: **все три раздела согласованы**. Следующий шаг — архитектура.

---

## 1. Продуктовые требования (v1)

### 1.1 Суть продукта

Веб-сервис собственной базы знаний: страницы с текстом, организованные в дерево
произвольной вложенности, со ссылками между собой. Работает оффлайн и
синхронизируется при появлении сети. Данные хранятся в S3 с локальной копией.

В v1 сервисом пользуется один человек — владелец. Регистрации нет, доступ на
запись закрыт простой защитой. При этом модель данных, хранилище и код
изначально мультитенантные: добавление регистрации и вторых пользователей
не должно требовать миграции данных или переписывания.

### 1.2 Мотивация

Спортивный интерес плюс неудовлетворённость Notion (тяжёлый, глючный).
Гипотеза: при сознательно минимальных требованиях можно получить инструмент
быстрее и приятнее. Явная **нецель** — повторять Notion по объёму функций.

### 1.3 Пользователи и роли

| Роль | Кто | Что может |
|---|---|---|
| Владелец | Один человек (я) | Всё: создавать, править, переносить, удалять страницы; менять видимость базы |
| Анонимный читатель | Любой, у кого есть ссылка на публичную базу | Только читать |

Нет: команд, ролей, шаринга базы конкретным людям, совместного редактирования.

### 1.4 Ключевые сценарии

1. Создать страницу, написать текст, сохранить.
2. Построить дерево: вложить страницу в страницу, перенести ветку.
3. Сослаться с одной страницы на другую.
4. Открыть базу с другого устройства — увидеть актуальную версию.
5. Поработать оффлайн (читать и править); при появлении сети — автоматический синк.
6. Посмотреть историю страницы и откатиться к прошлой версии.
7. Сделать базу публичной / вернуть в закрытую.

### 1.5 В границах v1

- **Контент:** страницы с текстом и базовым форматированием — заголовки, списки,
  код, цитаты, ссылки. **Только текст; изображений, файлов и вложений нет.**
- **Структура:** иерархия страниц без ограничения глубины, перенос веток.
- **Связи:** ссылки между страницами внутри базы.
- **Доступ:** регистрации нет; редактирование защищено простым секретом,
  известным только владельцу.
- **Видимость:** база целиком публична (чтение по прямой ссылке) либо полностью
  закрыта. Промежуточных прав нет.
- **Оффлайн:** чтение и правка без сети, синхронизация при подключении,
  разрешение конфликтов.
- **История:** версии страницы с возможностью отката.
- **Хранение:** S3 как источник истины + локальная копия.
- **Клиент:** только веб, с адаптивной вёрсткой под телефон.

### 1.6 Вне границ v1

Отложено сознательно, порядок — примерный приоритет:

- **Поиск** по названию и содержимому *(ближайший кандидат на v2)*.
- Регистрация и реальные вторые пользователи *(архитектурно заложено, UI — потом)*.
- Мобильное приложение, затем десктопное.
- Изображения, файлы, вложения, эмбеды.
- Базы данных и представления в стиле Notion (свойства, фильтры, сортировки,
  доски, календари).
- Совместное редактирование в реальном времени, комментарии, упоминания.
- Шаринг базы конкретным людям, права на отдельные страницы, роли.
- Публичная индексация, листинг публичных баз, кастомные домены.
- Плагины, интеграции, внешнее API.

### 1.7 Зафиксированные решения

Приняты как минимально достаточные; пересмотреть можно в любой момент.

- **Одна база у владельца** в v1. Модель данных допускает несколько баз
  на пользователя, но UI управления ими не делаем.
- **Видимость задаётся на всю базу**, не на отдельную страницу или поддерево.
- **Публичная база = доступ по прямой ссылке** («unlisted»): каталога публичных
  баз нет, поисковую индексацию не подразумеваем.

### 1.8 Критерии готовности v1

- Владелец ведёт настоящую базу знаний в microdocs вместо Notion.
- Правка на одном устройстве появляется на других без ручных действий.
- Правка, сделанная оффлайн, не теряется и корректно вливается после подключения.
- История страницы есть, откат к прошлой версии работает.
- Потеря сервера не означает потерю данных: содержимое лежит в S3 и локально.
- Посторонний не может отредактировать чужую базу и не может прочитать закрытую.

## 2. Функциональные требования (v1)

### 2.1 Страница

| FR | Требование |
|---|---|
| FR-1 | Страница имеет неизменяемый идентификатор, не зависящий от заголовка и положения в дереве |
| FR-2 | У страницы есть отдельное поле заголовка, не являющееся частью тела. Пустой заголовок отображается как «Без названия» |
| FR-3 | Тело страницы — форматированный текст: абзацы, заголовки уровней 1–3, маркированные и нумерованные списки, чек-листы, код (строчный и блоком), цитаты, горизонтальный разделитель, жирный/курсив/зачёркнутый, ссылки |
| FR-4 | Страница хранит время создания и время последнего изменения |
| FR-5 | Страница может быть пустой — и по заголовку, и по телу |

Исходник тела страницы — Markdown.

### 2.2 Дерево

| FR | Требование |
|---|---|
| FR-6 | База содержит список страниц верхнего уровня; каждая страница может иметь дочерние — глубина не ограничена |
| FR-7 | Порядок соседних страниц задаётся вручную и сохраняется; новая страница добавляется в конец списка соседей |
| FR-8 | Страницу можно перенести в другого родителя или на верхний уровень — вместе со всем поддеревом |
| FR-9 | Перенос страницы внутрь собственного поддерева запрещён |
| FR-10 | Дерево отображается как навигация, ветки сворачиваются и разворачиваются |

### 2.3 Ссылки между страницами

| FR | Требование |
|---|---|
| FR-11 | В теле страницы можно поставить ссылку на другую страницу той же базы; ссылка привязана к идентификатору, а не к заголовку |
| FR-12 | Ссылка отображает актуальный заголовок целевой страницы — переименование цели не ломает ссылку |
| FR-13 | Ссылка на удалённую страницу отображается как нерабочая, а не молча исчезает |
| FR-14 | Поддерживаются обычные внешние URL |

### 2.4 Создание, изменение, удаление

| FR | Требование |
|---|---|
| FR-15 | Страница создаётся на верхнем уровне или как дочерняя к указанной |
| FR-16 | Изменения сохраняются автоматически, без явной кнопки «Сохранить» |
| FR-17 | Удаление — мягкое: страница уходит в корзину вместе с поддеревом и восстанавливается оттуда |
| FR-18 | Из корзины страницу можно удалить окончательно, явным действием |

### 2.5 Редактор

| FR | Требование |
|---|---|
| FR-19 | Редактор показывает отформатированный результат, а не разметку; исходником страницы остаётся Markdown |
| FR-20 | Форматирование применяется по ходу набора: `# `, `- `, `1. `, `> `, `- [ ] `, ` ``` `, `**жирный**` и т. п. превращаются в соответствующий элемент |
| FR-21 | Форматирование доступно и горячими клавишами (жирный, курсив, ссылка, код) |
| FR-22 | Цикл «разобрать → отредактировать → сохранить» не искажает содержимое: неизменённая страница после открытия и закрытия остаётся байт-в-байт прежней |
| FR-23 | Конструкции Markdown вне поддерживаемого набора (FR-3) не теряются: они сохраняются в исходнике, даже если редактор не умеет их показать |
| FR-24 | Вставка из буфера сохраняет базовое форматирование, если это Markdown или простой текст |

### 2.6 История версий

| FR | Требование |
|---|---|
| FR-25 | Версия страницы фиксируется по завершении сеанса правки, а не на каждое нажатие клавиши |
| FR-26 | История показывает список версий с датой и временем |
| FR-27 | Любую версию можно открыть и посмотреть её содержимое |
| FR-28 | Любую версию можно восстановить; восстановление создаёт новую версию, а не стирает историю |
| FR-29 | История покрывает заголовок и тело страницы. Перемещения по дереву не версионируются |
| FR-30 | История удалённой страницы сохраняется, пока страница в корзине, и восстанавливается вместе с ней |

### 2.7 Оффлайн и синхронизация

| FR | Требование |
|---|---|
| FR-31 | После первой загрузки база доступна целиком без сети — и на чтение, и на правку |
| FR-32 | Синхронизация автоматическая: без сети правки копятся локально, при появлении сети уходят на сервер |
| FR-33 | Интерфейс всегда показывает состояние: синхронизировано / есть несинхронизированные правки / нет сети |
| FR-34 | При расхождении версий одной страницы актуальной становится пришедшая на сервер последней. Автоматического слияния текста нет |
| FR-35 | Вытесненная версия не теряется: она попадает в историю страницы с пометкой, что пришла с другого устройства |
| FR-36 | Расхождения в структуре дерева (страницу перенесли на двух устройствах по-разному) разрешаются тем же правилом — побеждает последнее пришедшее изменение |
| FR-37 | Удаление и восстановление страниц синхронизируются наравне с правками |
| FR-38 | Незавершённая синхронизация не блокирует работу: пользователь продолжает читать и править |

### 2.8 Доступ и владение

| FR | Требование |
|---|---|
| FR-39 | Каждая страница принадлежит ровно одной базе, каждая база — ровно одному владельцу; любая операция выполняется в границах одной базы |
| FR-40 | Любое изменение требует владельческого секрета; без него доступ только на чтение |
| FR-41 | Владелец переключает базу между «публична» и «закрыта» |
| FR-42 | Публичную базу читает кто угодно по прямой ссылке, без секрета и регистрации |
| FR-43 | Закрытая база не читается без секрета; посторонний не должен по ответу сервиса понять, существует ли она |
| FR-44 | Корзина, история версий и состояние синхронизации анонимному читателю недоступны даже в публичной базе |

### 2.9 Решения, принятые по ходу

- Порядок соседних страниц — ручной, не алфавитный.
- Заголовок — отдельное поле, а не первый заголовок тела.
- У базы список корневых страниц, а не одна страница-корень.
- Обратные ссылки (backlinks) не делаем.
- Версия фиксируется по паузе в правках или уходу со страницы.
- Версии не чистятся автоматически: текста мало.
- Слэш-меню в стиле Notion не делаем; хватает набора по FR-20.
- Конфликты разрешаются без участия пользователя: last-wins плюс история.

## 3. Нефункциональные требования (v1)

Два сквозных следствия, от которых зависит остальное:

- **История версий строится на версионировании объектов в S3**, а не на собственном
  механизме. FR-25…FR-30 и FR-35 ложатся на него напрямую.
- **Скорость S3 не влияет на отзывчивость чтения**: база доступна оффлайн (FR-31),
  страницы открываются из локальной копии. S3 определяет только холодную загрузку
  и время синхронизации.

### 3.1 Объёмы и отзывчивость

| NFR | Требование |
|---|---|
| NFR-1 | База рассчитана на порядок ~2000 страниц; страница — до ~100 КБ текста |
| NFR-2 | Открытие страницы и навигация по дереву идут из локальной копии и не зависят от сети |
| NFR-3 | Набор текста остаётся плавным на странице предельного размера |
| NFR-4 | Холодная загрузка базы на новом устройстве — единицы секунд; отдельной оптимизации сверх того, что даёт S3, не делаем |
| NFR-5 | Отправка правки на сервер — единицы секунд при нормальной сети |

### 3.2 Сохранность данных

| NFR | Требование |
|---|---|
| NFR-6 | Источник истины — объектное хранилище S3 в MWS Cloud; гарантии сохранности берём те, что даёт хранилище, своих слоёв поверх не строим |
| NFR-7 | Версионирование объектов включено и является механизмом истории страниц |
| NFR-8 | Правка, подтверждённая пользователю как сохранённая, переживает падение сервиса |
| NFR-9 | Правка, сделанная оффлайн, переживает закрытие вкладки и перезагрузку устройства до момента синхронизации |
| NFR-10 | Восстановление базы возможно из одного лишь содержимого бакета, без работающего сервиса |

### 3.3 Доступность

| NFR | Требование |
|---|---|
| NFR-11 | При недоступном сервисе или сети пользователь продолжает читать и править локальную копию; синк догоняет позже |
| NFR-12 | Плановой доступности с процентами не задаём — сервис личный, простой сервиса не блокирует работу |

### 3.4 Безопасность

| NFR | Требование |
|---|---|
| NFR-13 | Секрет владельца закрывает закрытую базу и на чтение, и на запись |
| NFR-14 | Весь трафик только по HTTPS; секрет не передаётся в URL и не попадает в логи |
| NFR-15 | На сервере хранится не сам секрет, а его хеш |
| NFR-16 | Подбор секрета ограничен: частота попыток лимитируется, длина секрета исключает перебор |
| NFR-17 | Бакет закрыт от публичного доступа и листинга; содержимое отдаётся только через приложение, включая публичные базы |
| NFR-18 | Локальная копия на устройстве не шифруется — доступ к разблокированному устройству считаем доверенным |

### 3.5 Совместимость

| NFR | Требование |
|---|---|
| NFR-19 | Поддерживаются последние версии Chrome, Safari, Firefox, Edge; о старых браузерах не заботимся |
| NFR-20 | Вёрстка адаптивна от ширины 360 px до десктопной |
| NFR-21 | Оффлайн-режим опирается на современные браузерные API без полифилов для старых движков |

### 3.6 Эксплуатация

| NFR | Требование |
|---|---|
| NFR-22 | Всё разворачивается в MWS Cloud: и приложение, и хранилище |
| NFR-23 | Стоимость эксплуатации — на уровне личного пет-проекта; дорогих managed-сервисов избегаем |
| NFR-24 | Выкатка автоматическая из репозитория, без ручных шагов на сервере |
| NFR-25 | Наблюдаемости сверх логов приложения в v1 не делаем |

### 3.7 Ограничения на вырост

| NFR | Требование |
|---|---|
| NFR-26 | Данные в хранилище разложены по тенантам с самого начала: появление второго пользователя не требует миграции |
| NFR-27 | Серверная часть общается с клиентом через API, пригодный для будущих мобильного и десктопного клиентов |
| NFR-28 | Формат хранения не препятствует добавлению поиска позже |
